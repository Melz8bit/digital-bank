### `requireAuth` middleware (`api/src/middleware/requireAuth.ts`)
Built step by step, catching several real bugs along the way:
- Initially imported/used Express's lowercase `request` export (an internal prototype object) and tried reading a header at module scope, before any middleware function existed — corrected to a proper `(req, res, next)` middleware function reading `req.headers.authorization` per-request.
- `.startsWith('Bearer')` missing the trailing space — would have accepted a malformed `"Bearerxyz"` prefix.
- Off-by-one on `authHeader.slice(6)` — `'Bearer '` is 7 characters, so this left a stray leading space on the extracted token, which would have caused every legitimately-formatted token to fail `jwt.verify()`. Fixed to `slice(7)`.
- Re-called `jwt.verify()` a second time outside the try/catch while trying to fix a variable-scoping issue — would have turned a handled `401` case into an unhandled exception. Fixed by declaring `payload` before the `try` and assigning inside it.
- Talked through the `jwt.verify()` return type (`string | JwtPayload`) and why the `string` branch, while unreachable given how this codebase always signs objects, still needs handling defensively (401) since the type system can't know that.
- Caught a real gap: initial version didn't check whether `payload.sub` was present after narrowing away the `string` case — a validly-signed token without a `sub` claim would have set `req.parentId = undefined` and still called `next()`. Fixed with a combined `typeof payload == 'string' || !payload.sub` guard.
- Designed the `req.parentId` typing question explicitly: chose declaration merging (`api/src/types/express.d.ts`, `declare global { namespace Express { interface Request { parentId?: string } } }` + `export {}`) over `res.locals`, for full type-checking on `req.parentId` across route handlers. Confirmed `tsconfig.json`'s `include: ["src"]` already picks it up with no extra config.
- Fully typechecks; not yet exercised against a live route since no routes are wired up yet.

### `auth.routes.ts` — `POST /signup` (in progress)
- Router created and properly exported (`export default router`) after an initial version had no export at all.
- Built request validation with `SignupInputSchema.safeParse(req.body)` and `treeifyError()` (zod v4) for structured 400 responses.
- Caught several real bugs building the try block:
  - Missing `await` on `signup(result.data)`.
  - `signup()` resolves to `{ token, parent }`, not just a token — needed destructuring instead of assigning the whole object to a variable named `token`.
  - Found and explained a genuinely sneaky one: an unawaited/undestructured draft referenced a bare `parent` identifier that had never been declared locally, yet `tsc` didn't flag it — because this project's `tsconfig.json` has no explicit `lib` override, so TypeScript's default library set for `target: ES2020` includes `DOM`, which declares an ambient global `parent: Window`. The code typechecked against that accidental global and would have thrown `ReferenceError: parent is not defined` at runtime in actual Node.js. Flagged `"lib": ["ES2020"]` (no DOM) as a worthwhile future tsconfig change to catch this class of bug at compile time; not applied yet.
  - Built out the catch block mapping `EMAIL_TAKEN`→409, `INVITE_SIGNUP_NOT_IMPLEMENTED`→501, unknown→500 — caught a version where the 500 fallback was nested inside `if (err instanceof Error)`, meaning a non-`Error` throw would fall through with no response sent at all (the request would hang). Fixed by moving the fallback return outside that `if`.
  - Talked through user-enumeration risk on the `EMAIL_TAKEN` message specifically — concluded it's an accepted, standard tradeoff for signup (unlike login, which already stays deliberately generic) given this app has no email-verification flow to hide behind, and the low threat model of a personal family app. Landed on real, useful message strings for all three branches instead of ones that just restated the HTTP status code.
- `POST /signup` handler complete and typechecks clean. Not yet mounted in `app.ts`, not yet hit with a real HTTP request.
