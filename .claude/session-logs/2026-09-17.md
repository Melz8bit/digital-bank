## Phase 1 — PIN set/verify + rate limiting (built and shipped)

### Design discussion before writing code
- Landed on: 5 wrong attempts → 5-minute lockout; `pin_attempts` resets to 0 only on a *correct* verify, not just when the lockout window expires; PIN routes live in their own `pin.routes.ts` (separate concern from auth — proves *access to Settings*, not *who you are*); PIN **change** (requiring the old PIN) is explicitly out of scope for now, deferred to the later account-settings phase — this pass is set + verify only.
- Discovered the schema already had `pinHash`/`pinAttempts`/`pinLockedUntil` on the **`families`** table (not `parents`) from Phase 0 scaffolding — confirmed this was the right call, since the PIN gates Settings for the whole family, shared across co-managing parents. No migration needed.
- Worked through how PIN routes get `familyId` when `requireAuth` only sets `req.parentId`: chose "look up on demand" (an internal `getFamilyForParent(parentId)` helper does a quick two-step select) over embedding `familyId` in the JWT, to keep the already-verified `authService.ts`/`requireAuth.ts` untouched.
- Worked through the second-parent-joining-via-invite-code flow: concluded no PIN step belongs in signup/login at all. First parent (creates a new family) gets prompted to set the PIN immediately after signup; second parent (joins via invite code) skips it entirely, since the PIN is already set. This is a client-side routing decision based on which signup branch was used — not something the API needs to encode. `GET /pin/status` still exists as a general-purpose check for whenever the Settings tab is opened later.

### `pinService.ts`
- `getFamilyForParent()` — internal helper, two-step select (parent → family) shared by all three exported functions.
- `getPinStatus(parentId)` — returns `{ pinSet: !!family.pinHash }`.
- `setPin(parentId, pin)` — guards with `PIN_ALREADY_SET` if a hash already exists (mirrors `EMAIL_TAKEN`), otherwise `bcrypt.hash(pin, 12)` and writes it.
- `verifyPin(parentId, pin)` — the one with real logic. Caught a genuine bug mid-build: the first draft ran two unconditional `db.update()` calls back-to-back regardless of whether the PIN matched, so a correct-PIN reset to `{ pinAttempts: 0 }` was immediately overwritten by an unconditional increment right after it. Fixed with a real `if (pinMatch) {...} else {...}`, plus `.returning()` in the failure branch so the lockout-threshold check reads the freshly-written attempt count instead of the stale local variable from before the write.
- Talked through why the local `family` object doesn't auto-sync with the database after an `update()` — it's a snapshot from the `SELECT`, not a live reference — and when `.returning()` is actually needed (only if you read the fresh value afterward, which the lockout check does).

### `pin.routes.ts`
- `GET /status`, `POST /set`, `POST /verify`, all behind `requireAuth`.
- Caught several real bugs building `/status` first: missing `requireAuth` entirely (so `req.parentId` wouldn't exist), validating `req.body` against `PinInputSchema` on a route that takes no input at all, and passing the wrong argument (`req.body` instead of `req.parentId`) to `getPinStatus()`.
- `/set`: built cleanly on the first real pass — `requireAuth`, validate, call `setPin()`, `201` on success, `PIN_ALREADY_SET`→409.
- `/verify`: needed two rounds of fixes — route was initially named `/verifyPin` (redundant under the `/pin` prefix, inconsistent with `/status`/`/set`), success status was `201` instead of `200` (nothing is created by a verify), and all three error branches initially mapped to `409` instead of being distinguished. Landed on `INVALID_PIN`→401 (mirrors `INVALID_CREDENTIALS` on `/login`), `PIN_LOCKED`→423 (the literal HTTP status for "resource is locked"), `PIN_NOT_SET`→409 (user's own call — state conflict).
- Mounted with `app.use('/pin', pinRouter)` in `app.ts`.

### End-to-end verification against real dev Postgres
- `GET /pin/status` before/after `POST /pin/set` — `false` → `true`.
- `POST /pin/set` a second time on the same family — `409 PIN_ALREADY_SET`.
- `POST /pin/verify` with the correct PIN — `200`.
- 4 wrong-PIN attempts — `401` each; 5th attempt trips the lockout — `423`.
- Correct PIN submitted while locked — still `423` (lockout checked before comparison).
- `POST /pin/verify` against a fresh family that never set a PIN — `409 PIN_NOT_SET`.
- All test families/parents cleaned up via `psql` afterward.
