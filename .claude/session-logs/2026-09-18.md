## Phase 1 — Client: login/signup screens (started)

### Scoping discussion before writing code
Nothing client-side existed yet beyond the placeholder tab shell from Phase 0 — no React Query, no Zustand, no auth screens, no token storage. Talked through three decisions before installing anything:

- **Token storage**: `expo-secure-store` doesn't work on web, and this app targets both Android and web. Chose `@react-native-async-storage/async-storage` everywhere (one code path, works identically on both platforms) over a native-SecureStore/web-localStorage split — matches the low-threat-model reasoning already established for this app (same reasoning used for the `EMAIL_TAKEN` enumeration tradeoff on signup).
- **Route gating**: Expo Router 6's `<Stack.Protected guard={...}>` to declaratively gate the existing `(tabs)` group behind auth state, with a new `(auth)` group holding login/signup — cleaner than hand-rolled redirect logic in a `useEffect`.
- **Packages**: installed `@tanstack/react-query`, `zustand`, `@react-native-async-storage/async-storage` into the `app` workspace.

### `app/store/authStore.ts` (in progress, not yet complete)
Started walking through zustand's `persist` middleware in detail, since it's the first time this codebase has used zustand at all:
- Defined the `AuthState` interface first, separately from the store itself: `token`, `parent`, `hasHydrated`, plus `setSession`/`clearSession`/`setHasHydrated` actions. Used `AuthState['parent']` (indexed access) in `setSession`'s signature to reuse the `parent` field's type instead of retyping the object shape.
- Explained why `create<AuthState>()` is called with the generic and empty parens before the actual store-creator argument — TypeScript can't infer the generic through the `persist` wrapper on its own, so it has to be supplied explicitly up front; the "double call" is a known curried-generics quirk, not a typo.
- Explained the store-creator function shape (`(set) => ({...})`) and that `set` shallow-merges a partial object into state, unlike `useState`.
- Explained the `persist` config's second argument: `name` (the AsyncStorage key), `storage: createJSONStorage(() => AsyncStorage)` (how zustand serializes into AsyncStorage's string-only API), and `onRehydrateStorage` (returns a callback that fires once persisted state has actually loaded back in — the hook for flipping `hasHydrated` to `true`).
- Explained *why* `hasHydrated` matters at all: AsyncStorage reads are async, so on a cold app start there's a brief window before the persisted token loads back in. Without tracking that, `Stack.Protected`'s `guard={!!token}` would read `token` as `null` for a split second even for an already-logged-in parent, flashing the login screen before snapping to the tab shell.
- Left one open question unanswered when the session ended: whether to add zustand's `partialize` option to exclude `hasHydrated` from what actually gets written to storage (harmless either way since it gets immediately overwritten on next load, just sloppy without it).

Session ended with only the `AuthState` interface typed into `authStore.ts` — the actual `create<AuthState>()(persist((set) => ({...}), {...}))` body (state defaults, the three actions' `set(...)` calls, and the `persist` config) is not yet written.
